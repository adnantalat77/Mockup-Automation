# Application architecture

The browser talks only to the local Express API. Uploads are held in memory while Sharp validates their decoded content, then written under `data/` with UUID filenames. No original filename is used as a filesystem path.

- `apps/web`: React/Vite dashboard on port 3000.
- `apps/api`: Express upload, asset, validation, and Sharp compositing endpoints on port 3001.
- `packages/shared`: transport types shared by both applications.
- `data/uploads`: original backgrounds and garments (ignored by Git).
- `data/generated`: generated PNG previews (ignored by Git).

SQLite is intentionally deferred because current metadata can be stored beside local assets. The dashboard's primary path is Shopify product selection, background upload, bulk generation, and guarded publishing or recovery. The legacy manual garment upload and standalone preview interface have been removed, while their API validation and Sharp compositing services remain available and support automated coverage and batch processing.

The executable API startup acquires a process-lifetime, OS-backed lock for the canonical data directory before constructing any persistent service. Canonical directory creation and `realpath` resolution necessarily precede acquisition, but no mutable application-state initialization does. On Windows this is an atomically bound named-pipe listener keyed by the SHA-256 of the `realpath`-resolved, case-folded directory identity. A losing process exits before asset initialization, batch recovery, or publication recovery; kernel handle closure releases ownership after crashes. HTTP shutdown, including completion of active requests, precedes lock release; failed shutdown retains ownership and concurrent shutdown callers share one attempt. This process boundary supplements, and does not replace, the `PublishingService` per-product in-memory lock. See [TASK020_SINGLE_INSTANCE.md](TASK020_SINGLE_INSTANCE.md).

The Release 1 Windows deployment uses the installed Node.js 20.19+ runtime and compiled workspace output; it does not run Vite. `Start-Mockup-Automation.cmd` validates `.env`, dependencies, build output, the explicit data directory, and either read-only (`SHOPIFY_PUBLISHING_ENABLED=false`) or fully gated publishing configuration. Express serves the built frontend on `127.0.0.1:3001`. A short-lived named mutex serializes launcher decisions for the installation/data identity but disappears automatically and never replaces the Task 020 lock.

Each startup has separate cryptographically random instance and shutdown capabilities plus a UUID. The ignored runtime record binds them to the launched PID, actual resolved installation, and canonical data directory. Reuse requires a constant-time authenticated loopback identity challenge whose response matches every recorded field and the caller’s expected paths; public health is insufficient. Stop performs the same challenge before presenting the distinct shutdown capability. Capabilities never appear in public health, URLs, browser code, shortcut arguments, or logs. Missing/corrupt records, stale or reused PIDs, path drift, fake services, challenge failure, and live-but-unreachable processes fail closed. Stale records are removed only when their PID is dead and no service responds. Failed stop preserves the process, runtime record, and data lock.

## Phase 2 Shopify read-only boundary

`ShopifyService` is backend-only. It reads optional credentials from the repository-root `.env`, uses the 2026-10 client-credentials endpoint, caches short-lived tokens in process memory, refreshes before expiration or once after a 401, and never returns tokens or credentials to the browser. Connectivity checks query `currentAppInstallation.accessScopes` and require `read_products`. Phase 2 read-only routes invoke no GraphQL mutations; Phase 4 mutation methods are separately gated by the publishing boundary below.

The API provides read-only status, cursor-paginated product title search, product detail, and transparent source-import routes. Search returns at most 100 complete matches and asks the operator to narrow broader searches instead of silently truncating them. Product and image GIDs are strictly validated. Remote images must use HTTPS on Shopify CDN hosts; redirects are followed manually and revalidated, authority components are rejected, response size is checked before and during streaming, and downloads time out. Decoded PNG/JPEG content and alpha pixels are checked with the existing Sharp validators.

Color mappings use only direct Shopify variant image or media associations. An image associated with one color is reliable; images associated with multiple colors or no variants are marked for manual review. Filenames and alt text are never used to infer mappings. Importing a transparent source writes a preserved local copy and does not change the Shopify product.

When Shopify variables are absent or incomplete, the status route reports the integration unavailable. Local upload and compositing APIs remain operational, but the dashboard cannot begin its Shopify-based bulk workflow.

## Phase 3 batch processing

Shopify product detail connections are cursor-paginated with a 20-page safety cap. Unique images are decoded and alpha-validated sequentially, with at most 250 relevant images retained. Batch creation accepts only a validated product GID and an existing local background UUID. It caps work at 50 colors and two active batches.

`BatchService` derives candidates exclusively from reliable Shopify variant/media associations. Exactly one compatible transparent candidate is queued; missing and conflicting mappings are persisted as manual-review skips. Two workers process colors concurrently. Each worker downloads and revalidates its source, reads the preserved background, calls the existing `compositePreview`, and writes a new preview without changing either source. Transient Shopify failures receive one retry.

The first successful generation also stores the validated transparent garment bytes unchanged as a local `garment` asset on the batch item. If a later complete-gallery publication has detached that Shopify source, a new batch can reuse the preserved source for the same product and color. This fallback applies only when Shopify has no single compatible transparent candidate; it does not override an ambiguous live mapping. Publishing revalidates the preserved asset's alpha content and fails closed if it is missing or invalid.

Batch JSON metadata is stored under ignored `data/batches/` and serialized per batch to prevent concurrent write races. On startup, interrupted queued or processing items become failed review items rather than being resumed silently. Cancellation sets a durable flag, prevents new items from starting, and lets in-flight processing complete safely. Individual successful mappings can be regenerated after the batch stops.

ZIP export includes only successful previews, uses unique sanitized color filenames, performs no image transformation, and rejects archives whose input previews exceed 150 MB. The archive is assembled in memory, so this limit is a deliberate local safety bound.

## Image guarantees

The API decodes files with Sharp instead of trusting extensions or browser MIME types. Garment PNGs are converted to raw RGBA for alpha-pixel inspection. Validation requires at least 16 meaningful alpha pixels or 0.1% of the image, whichever is greater (bounded by total pixels), using alpha values at or below 250. This rejects opaque files and isolated near-opaque edge artifacts while retaining legitimate partially transparent antialiasing.

Backgrounds are auto-oriented from EXIF metadata before the output dimensions are read. Preview generation uniformly scales the complete garment only when it is larger than the normalized background, centers it, never crops or stretches it, and writes a new high-quality PNG. Input buffers and stored source files are not overwritten. Asset lookup accepts only strict UUID values generated by the server.

The frontend commits a new background selection only after server validation succeeds. A failed replacement clears the browser file input, retains the last validated background, and explicitly reports that the current selection was retained. Shopify source import reports its preserved local copy inline; generated comparisons are presented in the bulk gallery rather than a standalone preview section.

## Phase 4 publishing boundary

`PublishingService` is the only service that coordinates Shopify mutations. It accepts only completed Phase 3 batches, revalidates the current product mappings and all generated PNGs, and serializes publication or rollback work per product. Express protects every publishing route with a server feature flag, a 32-character minimum shared authorization secret, an allowlisted local browser origin, explicit confirmation text for mutations, and a live check for `read_products`, `write_products`, and `write_files`. Credentials and access tokens remain inside `ShopifyService`.

New publication is restricted to the exact disposable draft test product or an exact Product GID in `SHOPIFY_PUBLISH_PRODUCT_IDS`. The allowlist is parsed and strictly validated at startup and is empty by default. A real product requires the exact server-generated confirmation `PUBLISH <product GID>`. Rollback remains tied to an existing immutable operation so an operation is not stranded if product status changes after publication.

The replacement sequence is staged upload, `fileCreate`, `MediaImage.fileStatus` polling, `fileUpdate(referencesToAdd)`, then `productVariantsBulkUpdate` with the generated `mediaId` for every size variant mapped to the color and `allowPartialUpdates: false`. After every generated association is checkpointed, `fileUpdate(referencesToRemove)` detaches each original file from only this product, without a global delete. `productReorderMedia` then orders generated media in batch color order. A fresh complete snapshot must equal the generated-only media order and every variant must reference its color's generated ID before publication is successful. Original IDs, ordering, and variant associations remain immutable rollback evidence.

Media reorder polling uses the dedicated QueryRoot `job(id:)` field rather than `node(id:)`; Shopify's `Job` type does not implement `Node`. The service requires a returned job and waits for `done` with a 20-attempt, 500 ms bounded poll before reading final product ordering. On recovery from an interrupted removal or reorder, the complete live snapshot may contain the not-yet-detached subset of immutable originals plus operation-created media, but no unrelated media or variant drift. Already-detached originals and completed generated associations are reconciled and checkpointed without repeating their mutations. If generated media are already in target order, reorder is checkpointed complete; otherwise only the reorder mutation is retried.

Fresh publication and partial recovery use separate API contracts. Fresh readiness applies the first-publication preflight rules and `publish` always creates a new operation; both are blocked by an existing nonterminal product operation. Recovery is addressed by immutable operation ID plus batch ID, is limited to `partial` operations, and validates a complete live snapshot through the existing fail-closed comparison rules. `resume` validates and reconciles again in the product-locked continuation path and never creates an operation. Abandoned, conflicted, completed, wrong-batch, and externally changed operations cannot be resumed.

Release 1 supports one background-replacement publication per product. Publication startup re-runs preflight and unresolved-operation checks while holding the product lock, persists checkpoint zero, and keeps the lock through mutation and final verification. A durable `published`, `rolled_back`, or `rolled_back_files_retained` operation prevents another independent publication even after restart; an unresolved operation must use recovery or rollback instead. Historical predecessor fields remain readable for checkpoint compatibility, and verified abandonment remains limited to the disposable test-reset workflow.

Recovery metadata lives in ignored `data/publications/<operation UUID>/`. Each JSON checkpoint is first written to a uniquely named temporary file and atomically renamed to a monotonically increasing final filename. Checkpoint `000000.json` contains the original ordered product media IDs, original variant-media associations, generated preview IDs, mappings, and operation identity before any mutation. Every mutation is bracketed by an intent checkpoint and a result checkpoint. Startup validates structure, ignores temporary or malformed checkpoints, and loads the newest complete checkpoint.

Recovery integrity additionally rejects duplicate product media, duplicate variant identities, duplicate variant associations, incomplete snapshots, contradictory item ownership, unsupported state or intent values, and Task 019 records with incomplete evidence. Variant comparison is by exact GID set and per-variant association rather than array position or count. A syntactically complete but contradictory newest checkpoint fails startup; only incomplete JSON or temporary writes may fall back. Publication and rollback terminal transitions independently require exact live state, complete durable steps, and no unresolved mutation intent. See [TASK021_RECOVERY_INTEGRITY.md](TASK021_RECOVERY_INTEGRITY.md).

Asset, batch, and checkpoint persistence uses flushed same-directory temporary files followed by atomic promotion. Asset reads enforce metadata identity and SHA-256 evidence, while malformed batch startup fails closed. A failed publication checkpoint blocks that product from every later mutation intent or state transition until restart reconciliation. Offline backup creation and restoration share the Task 020 lock, reject path collisions and links/reparse points, validate referenced assets and recovery metadata, preserve the prior live tree, and place the reconciliation marker in staging before promotion. While that marker exists, every publication, recovery, rollback, abandonment, and finalization transition is server-blocked; Task 022 provides no marker-clearing bypass. See [TASK022_OPERATIONAL_RESILIENCE.md](TASK022_OPERATIONAL_RESILIENCE.md).

Garment-source trust is tracked independently from publication recovery. New garment asset metadata and batch items contain provenance schema version 1, exact product/color/MediaImage identity, a non-secret stable source reference, acquisition and validation times, dimensions, transparency evidence, and SHA-256 of actual downloaded bytes. Generation evidence binds source, background, and preview hashes. Historical records without these optional fields remain readable but are unverified for any new publication.

Preserved sources may be reused after gallery replacement only for inspection preview generation. `reusePreservedSources()` marks them `historical_unverified`; it never promotes local integrity into current-artwork evidence. Final publication preflight independently redownloads exactly one current reliable Shopify source for every color, validates its variant associations, format and alpha transparency, and requires its byte hash to equal provenance. It also rehashes local source, background, and preview assets. This preflight runs again inside the publication lock before checkpoint creation, closing batch restart and readiness-to-publish time-of-check gaps.

Task 019 operations snapshot provenance and generation evidence in checkpoint zero. Resume revalidates current sources inside the product lock and requires the batch preview, variants, provenance, and generation evidence to match that immutable snapshot; regenerated or edited batches cannot authorize an older operation. Historical operations without `sourceValidationSchemaVersion` keep their original recovery behavior. Preview bytes are rehashed immediately before staged upload.

Rollback first requires the explicit strongly typed mode `no_global_delete`, then compares current media with the union of snapshot media and media created by the operation. Missing or invalid mode values fail before Shopify state is read. Unrelated additions or variant-association drift produce a conflict requiring manual review. For replacement operations, rollback reattaches retained originals, restores every immutable variant association, removes generated product references, and restores exact original ordering. It deliberately retains generated global files and never calls `verifyFileDeletionSafe` or `fileDelete`. Partial failures remain checkpointed and retryable only after live reconciliation.

An operation whose product restoration succeeded but whose generated files were preserved for uncertain global ownership can be explicitly finalized as `rolled_back_files_retained`. Read-only verification requires the designated disposable draft product or allowlisted real product, structured per-item cleanup evidence, a complete immutable snapshot, exact live original media ordering, exact live variant identity and associations, and absence of every generated media ID from the product and variants. The finalization request repeats that verification inside the product lock, performs no Shopify mutation, and appends evidence containing the status transition, confirmation, verified originals, retained generated IDs, and cleanup conflicts. It resolves the recovery state without representing retained Shopify Content files as deleted, but it does not authorize a second Release 1 background replacement.

Generated-file cleanup evidence includes `retained_by_operator` with stable reason code `global_deletion_prohibited_by_operator`. Finalization accepts this outcome only when every generated file has the same deliberate-retention classification and the product exactly matches the immutable original snapshot. Historical `retained_ownership_unproven` outcomes remain supported. Mixed outcomes, cleanup failures, uncertain creation/deletion, and legacy unstructured conflicts fail closed. Historical finalized checkpoints remain readable without modification.

Historical checkpoints containing a persisted `delete_file` intent remain nonretryable: startup converts them to `cleanup_outcome_uncertain` and requires manual reconciliation. The supported `no_global_delete` path never creates such an intent. Retained-file finalization is permitted for the exact disposable Draft product or an exact currently allowlisted real-product GID. It verifies live identity, the complete restored graph, generated-reference absence, and consistent retained outcomes; it performs no Shopify mutation.

Restored data is guarded by `RESTORED_FROM_BACKUP.json`. The protected reconciliation endpoints enumerate every restored operation, reject nonterminal or uncertain intent evidence, and retrieve complete live product snapshots without mutation. For each product, the newest durable terminal operation defines the only accepted state: exact published gallery and generated variant mappings, or exact original gallery and variant mappings for rollback, retained-file rollback, and abandonment. Clearance requires the marker SHA-256 in the typed confirmation, writes reconciliation evidence atomically, obtains a second identical live snapshot, rechecks the marker bytes, and renames the marker to a preserved cleared record. Any read, persistence, drift, or rename failure leaves the active marker in place. Normal allowlist, source-freshness, authorization, origin, product-lock, and confirmation gates still apply afterward.

Release 1 deliberately uses current transparent Shopify media as the one-time workflow input. Eligibility still requires exact product identity, one reliable color mapping, the complete exact variant set, current attachment, stable media identity, meaningful alpha transparency, and byte-for-byte SHA-256 agreement with the preserved provenance and generated preview evidence. Detached historical sources and generated mockups cannot authorize publication. Independent Printful authentication, supplier registries, permanent reusable source libraries, and repeat replacement are future scope rather than Release 1 acceptance dependencies.

Publication snapshots use independent cursor loops for product media, product variants, and every variant's nested media connection. Missing, repeated, or excessive cursors fail the operation closed. Partial publication retries use the original snapshot, reconcile each known created media ID, detached original, and variant association against the live complete graph, and never repeat `fileCreate` after an uncertain response. New operations record `publicationMode: replace_gallery`; historical operations without that field retain append-style ordering compatibility.

A durable `create_file` intent without `createdMediaId` represents the crash window after the request may have reached Shopify but before its response could be checkpointed. Startup marks that item `uncertainCreation` and the operation `conflict`; the partial retry path applies the same check independently. This state cannot return to automatic file creation.

Rollback compares the complete live variant-media graph with the expected operation state before mutation. It removes only the current product reference, deliberately preserves the underlying generated file under `no_global_delete`, and records a structured retained-file conflict pending explicit finalization.

Rollback records `productRestored` independently from `cleanupConflicts`. This distinguishes a product whose original ordering and variant associations are fully restored from residual operation-created files that were deliberately preserved because exclusive ownership could not be proven.

For rollback, variants with one original association are grouped by original media ID and restored through `productVariantsBulkUpdate` before generated product references are removed. Originally unassigned variants use `productVariantDetachMedia`. More than one original association, mixed replacement results, or any association outside the immutable original/generated alternatives fails closed for manual review. Interrupted bulk replacements are reconciled from the complete live variant snapshot before another mutation is considered.

## Disposable test-operation abandonment

Abandonment is a narrowly scoped terminal transition for `gid://shopify/Product/15608846975264` only. The service also verifies the exact title `Mockup Automation - TEST ONLY` and `DRAFT` status. It accepts only partial, rollback-partial, or conflicted operations. A complete paginated live snapshot must exactly equal the immutable original media ordering and complete variant-association graph, and no recorded generated media ID may remain referenced by the product or any variant.

Validation performs reads only. Final abandonment re-runs validation while holding the per-product operation lock, then atomically checkpoints `abandoned`, `abandonedAt`, a user-supplied reason, and the complete verification evidence. Repeated calls are idempotent. Abandoned operations cannot resume or roll back, but their full prior checkpoint history remains unchanged. Stored Shopify Files are explicitly outside the proof: they are neither inferred safe nor deleted. Any other nonterminal operation for the product blocks a fresh publication.
